# Podman + systemd (Quadlet) Deployment

Deploys the runner stack on a Linux host where **systemd owns the containers**.
`install-podman.sh` generates [Quadlet](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html)
unit files, so the stack starts on boot and is operated with `systemctl` /
`journalctl` instead of a Compose project.

```bash
curl -fsSL https://raw.githubusercontent.com/bestony/self-hosted-action-runner/main/install-podman.sh | sudo bash
```

```bash
sudo bash install-podman.sh --non-interactive --dir /opt/github-runner \
  --skip-podman-install   # only when Podman is already installed
```

## Requirements

| Requirement | Why |
|---|---|
| Linux with systemd as PID 1 | Quadlet units are generated by `podman-system-generator` and managed by systemd |
| Podman >= 4.4 (rootful) | Quadlet (`.container` units) and the `podman-system-generator` binary |
| root or `sudo` | units live in the system Quadlet path and the stack runs as rootful Podman |
| `podman.socket` | workflow containers reach the host Podman API through the mounted socket |
| forwarded traffic from the container network | runners register and poll over HTTPS; a host firewall that drops forwarding breaks this |

`install-podman.sh` verifies all of the above, refuses to run on macOS/Windows
(`podman machine` has no host systemd to own units) and installs Podman through
the distribution package manager when it is missing.

The installer prints a one-line remediation for the two most common refusals:
a Podman version below 4.4 and a Podman build without Quadlet support.

### Container egress and host firewalls

Before starting the stack the installer runs a probe container on the stack
network and requires it to resolve and reach `https://api.github.com`. Without
that, registration fails with a five-minute `HttpClient.Timeout` per attempt and
the runner restart-loops.

Two firewall layouts break container egress on an otherwise healthy host:

* **ufw keeps its forward policy at `DROP`** (`DEFAULT_FORWARD_POLICY="DROP"`,
  `ufw status` reports `deny (routed)`). Podman 5.x installs its rules in
  nftables (`table inet netavark`), while ufw's `DROP` policy lives in the
  iptables `FORWARD` chain. Both hooks run at priority `filter`, iptables wins,
  and every packet from the container subnet is dropped: DNS still resolves
  (it is answered by the host) while TCP silently stalls.
* **Docker and Podman on the same host** make that ordering harder to predict,
  because Docker also writes its own `FORWARD` rules.

Allow the container bridge, then re-run the installer:

```bash
# the bridge is the network_interface of the stack network
podman network inspect <project>-net --format '{{.NetworkInterface}}'   # e.g. podman1

sudo ufw route allow in on podman1
sudo ufw route allow out on podman1
```

These rules are stored in `/etc/ufw/user.rules`, survive reboots and stay
narrower than switching `DEFAULT_FORWARD_POLICY` to `ACCEPT`. Re-check the
result at any time with:

```bash
podman run --rm --network <project>-net --entrypoint /bin/sh \
  <runner-image> -c 'getent hosts api.github.com && \
    curl -sS -m 20 -o /dev/null -w "reachable: HTTP %{http_code}\n" https://api.github.com/'
```

Any HTTP status means the path works. `403`/`429` are GitHub rate-limiting the
*anonymous* request from your address, which says nothing about the runner: the
runner authenticates with its own token and has a separate quota. The installer
probe is judged the same way — only a DNS failure or no response at all is
treated as broken. A hang (`errormsg` empty, no output) or curl's `000` is the
signature of dropped forwarding.

Set `GHR_SKIP_EGRESS_CHECK=yes` only when the host reaches GitHub through a
proxy that the probe cannot use; the probe already inherits `HTTP_PROXY`,
`HTTPS_PROXY` and `NO_PROXY`.

## File and unit layout

| Path | Content |
|---|---|
| `/etc/containers/systemd/<project>-runner-<n>.container` | Quadlet unit of runner instance `n` |
| `/etc/containers/systemd/<project>-cache.container` | Quadlet unit of the cache server (when enabled) |
| `<install-dir>/.env` | authoritative configuration record (0600) — the only file to edit |
| `<install-dir>/env/<unit>.env` | per-service environment file (0600), regenerated from `.env` |
| `<install-dir>/work/runner-<n>` | job workspace, mounted at the same absolute path inside the container |
| `<install-dir>/README.txt` | operations summary for this installation |
| `<install-dir>/install.log` | installer log (also used for troubleshooting failed steps) |

`<project>` is `ghr-<directory-name>-<hash>`: it is derived from the install
directory, so two installations never collide, and every unit belongs to exactly
one project prefix.

Unit base names equal container names: `<project>-runner-1` addresses both
`systemctl` (`<project>-runner-1.service`) and `podman logs <project>-runner-1`.

Unit files are **never** copied into the install directory: systemd reads the
Quadlet path directly, and a second copy would drift. Editing `.env` and
re-running the installer regenerates the units and the per-service env files.

Because Quadlet units are generated, `systemctl enable` does not apply to them
(systemd marks generated units transient). Boot startup is declared inside the
unit with:

```ini
[Install]
WantedBy=multi-user.target default.target
```

## Operations

```bash
# whole stack
sudo bash install-podman.sh --dir /opt/github-runner --status
sudo bash install-podman.sh --dir /opt/github-runner --start
sudo bash install-podman.sh --dir /opt/github-runner --stop
sudo bash install-podman.sh --dir /opt/github-runner --restart
sudo bash install-podman.sh --dir /opt/github-runner --upgrade

# one unit
systemctl status  ghr-<project>-runner-1.service
journalctl -u     ghr-<project>-runner-1.service -f
journalctl -u     ghr-<project>-runner-1.service --since "10 min ago"
podman logs -f    ghr-<project>-runner-1
podman exec -it   ghr-<project>-runner-1 bash

# diagnose unit generation
QUADLET_UNIT_DIRS=/etc/containers/systemd podman-system-generator --dryrun
systemd-analyze --generators=true verify ghr-<project>-runner-1.service
```

`--upgrade` pulls `RUNNER_IMAGE` / `CACHE_IMAGE` and restarts every unit on the
new image. Pinning a digest in `.env` (`RUNNER_IMAGE=...@sha256:...`) makes an
upgrade deterministic; `AUTO_UPDATE=1` additionally lets Podman pull the image
itself (Quadlet `AutoUpdate=registry`), which trades determinism for freshness.

Changing configuration is a two-step operation:

```bash
sudoedit /opt/github-runner/.env     # e.g. RUNNER_2_LABELS
sudo bash install-podman.sh --dir /opt/github-runner
```

The second command regenerates the units and per-service env files and restarts
nothing: run `--restart` (or `systemctl restart <unit>`) to apply the change to
running containers.

## Adding runners later

```bash
# append one target without touching existing instances
sudo GHR_MODE=add \
  GHR_RUNNER_1_URL="https://github.com/org/repo-b" \
  GHR_RUNNER_1_TOKEN="$(gh api -X POST repos/org/repo-b/actions/runners/registration-token --jq .token)" \
  bash install-podman.sh --non-interactive --dir /opt/github-runner
```

`GHR_MODE=reconfigure` replaces the instance list instead (instances that are no
longer configured have their units removed, so they stop consuming runner slots).

## Cache server modes

| Mode | Unit network config | `ACTIONS_RESULTS_URL` | When to use |
|---|---|---|---|
| `internal` (default) | `Network=<project>-net:alias=cache-server`, no published port | `http://cache-server:3000/` | Jobs run on the host Podman daemon (DooD) |
| `host` | `PublishPort=<port>:3000` on every host interface | `http://<host-ip>:<port>/` | Jobs that use `container:` need a URL reachable from inside a nested container |
| disabled (`GHR_CACHE=0`) | no cache unit, no cache URL | - | Cache is provided elsewhere |

Podman's default network has DNS disabled and container names of other containers
are not resolvable there, which is why the installer creates its own
`<project>-net` network. The `alias=` form of `Network=` is used instead of the
`NetworkAlias=` key because that key only exists since Podman 5.2, while the
network option works from 4.4. Both units also carry
`ExecStartPre=-podman network create <project>-net`, so a pruned network is
recreated on the next start.

The alias resolves through `netavark` (default since Podman 4.6) or through the
`dnsname` plugin on the legacy CNI backend; the installer warns when it detects
a backend that cannot resolve the alias.

`host` mode publishes the cache port on **every** interface. Keep it behind a
firewall or on a trusted network: anyone who can reach the port can read and
write cache entries.

## Running workflow containers (Docker-outside-of-Docker)

The runner container gets the host Podman socket mounted twice, as
`/var/run/docker.sock` and `/run/podman/podman.sock`, so both
`docker`-and `podman`-style tooling inside workflows finds a daemon. The image
entrypoint (see `entrypoint.sh`) auto-detects the socket group and adds the
runner user to it, so no unit-side `group-add` is required.

Limitations of the Podman API compatibility layer:

- The Podman service implements the **Docker API up to v1.40**. Newer API
  features (for example some `--platform` / BuildKit behaviours) are missing.
- `docker compose`-style nested orchestration is not supported: compose relies
  on API calls the compatibility layer does not implement. Workflows must create
  containers with `docker run` / `docker create` (or `podman` equivalents).
- The socket is mounted with `SecurityLabelDisable=true` because a mounted socket
  cannot be relabeled. On SELinux-enforcing hosts this disables label separation
  for the container; set `GHR_SELINUX=1` to keep labels when the socket mount is
  not needed, or `GHR_PODMAN_SOCKET=` (empty) to deploy runners without any Podman
  socket.

Because the socket belongs to rootful Podman, containers created by workflows run
as **host root**. Only run untrusted pull requests on such a runner when the
repository is trusted, or disable the socket mount.

## Uninstall and rollback

```bash
# stops units, removes units/containers, keeps .env, volumes and workspaces
sudo bash install-podman.sh --dir /opt/github-runner --uninstall

# also delete data (destructive: runner credentials, workspaces, cache)
sudo GHR_UNINSTALL_VOLUMES=yes GHR_UNINSTALL_WORKDIR=yes \
  bash install-podman.sh --dir /opt/github-runner --uninstall
```

Uninstall removes only units of this project prefix
(`<project>-runner-<n>.container`, `<project>-cache.container`), so other stacks
on the same host are untouched. `.env` stays in place: it records what was
deployed and keeps a reinstall reproducible. Delete it explicitly when the
deployment is retired for good:

```bash
sudo rm -rf /opt/github-runner
```

To return to the Docker path, uninstall the Podman stack first and deploy the
Compose variant into a **different** directory, because both installers write a
`.env` and job workspaces next to it:

```bash
sudo bash install.sh --non-interactive --dir /opt/github-runner-docker
```

## Troubleshooting

| Symptom | Check |
|---|---|
| `systemd does not know <unit>.service` | `QUADLET_UNIT_DIRS=/etc/containers/systemd podman-system-generator --dryrun` and `journalctl -u systemd-generators` |
| Unit exists but starts nothing | `systemctl status <unit>`; a failed pull shows up in `journalctl -u <unit>` |
| `Error: network name <project>-net already used: network already exists` on every start | Expected noise: Quadlet's `ExecStartPre=-podman network create` finds the network the installer pre-created. The `-` prefix makes systemd ignore the failure |
| Runner restarts every few seconds, log ends in `HttpClient.Timeout` or a five-minute stall | Containers cannot reach the GitHub API: see [Container egress and host firewalls](#container-egress-and-host-firewalls) |
| Runner registers, then exits | `journalctl -u <unit> -n 120`; `Http response code: NotFound ... runner-registration` (404) means a registration token that is invalid, expired (they last one hour) or was issued for a different scope than the URL — a repository token with an organization URL fails this way |
| `Start request repeated too quickly` and the unit stays `failed` | Only units generated before this behaviour was fixed hit it. `systemctl reset-failed <unit> && systemctl start <unit>`; regenerated units carry `StartLimitIntervalSec=0` and retry every `RestartSec=10` |
| Installer reports `Credentials are in place, but the runner did not report 'Listening for Jobs'` | The volume holds credentials but the runner never came online: `journalctl -u <unit> -f`. Usually a runner that was deleted in GitHub, or an entitlement problem in the organization |
| Cache unreachable from a job | `podman exec <runner> sh -c 'getent hosts cache-server; wget -q -O- http://cache-server:3000/'`; if the alias does not resolve, check `podman info --format '{{.Host.NetworkBackend}}'`; if it resolves but does not answer, check the cache unit |
| Workflows cannot create containers | `podman exec <runner> docker info`; a missing socket means `GHR_PODMAN_SOCKET` was empty at install time |
| Image tag does not update | `--upgrade` pulls and restarts; `AUTO_UPDATE=1` adds Quadlet `AutoUpdate=registry` |
